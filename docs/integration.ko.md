# 통합 가이드

> English: [integration.md](integration.md)

빌드 파이프라인이나 서버에서 컴파일러를 실행하고 출력을 클라이언트에 제공하는 방법을 설명한다. 여기의 모든 내용은 언어에 독립적이다. 세 포트는 동일하게 동작하며([`spec/SPEC.md`](../spec/SPEC.md)), 설치와 각 언어에 맞는 API 사용법은 포트별 README에 있다([TS](../js-cplr/README.ko.md) · [Python](../py-cplr/README.ko.md) · [Go](../go-cplr/README.ko.md)).

## 두 가지 운영 모드

**사전 컴파일(CLI)** — 빌드 또는 배포 시 `sdui-compile`을 실행하고 출력 디렉터리를 게시하여 정적으로 제공한다.

```sh
sdui-compile <sdui-root> --out <dir> [--pretty]
```

템플릿이 런타임이 아닌 배포 시 변경되는 경우에 적합하다. 산출물은 일반 파일이므로 무엇으로든 제공할 수 있고(nginx, S3+CDN, 앱의 에셋 라우트), 어떤 항목도 배포되기 전에 전체 컴파일을 검증한다. 깨진 템플릿은 사용자 요청이 아니라 빌드를 실패시킨다.

**프로세스 내 처리(라이브러리)** — 서버 시작 시 SDUI 루트에서 `ScreenRegistry`를 빌드하고 요청마다 해석한다.

```text
registry = ScreenRegistry.build(rootDir)     # compiles every screen; throws on any error
composed = registry.resolve(id, appVersion)  # -> { template, etag } or absent
```

서버가 템플릿을 소유하는 경우(모놀리스, 템플릿 핫 리로드 개발 루프, 또는 소스에서 바로 제공하려는 경우)에 적합하다. 레지스트리를 생성하면 **모든 항목을 즉시** 컴파일한다. 깨진 템플릿은 부팅을 실패시키고, 요청별 해석은 컴파일이 아니라 조회이다.

어느 방식을 사용하든 컴파일은 결정적이다. 어떤 포트에서든 같은 입력 바이트는 같은 출력 바이트와 같은 etag를 만든다.

## 산출물

```text
<out>/
  manifest.json
  screens/<id>/<templateVersion>.json    # one per distinct template version
```

`manifest.json`은 항상 2칸 들여쓰기로 보기 좋게 출력된다.

```json
{
  "home": {
    "versions": { "1.0.0": { "template": "1.0.0" },
                  "2.3.0": { "template": "2.0.0" } },
    "params": ["id"],
    "etags":  { "1.0.0": "be22f863ad4e95e0",
                "2.0.0": "0f3c5a9d1e7b2c44" }
  }
}
```

- `versions` — 앱 버전 임계 버전(threshold) → 에셋 버전. 아래에서 설명하는 버전 선택용 라우팅 테이블이다.
- `params` — 스크린에 선언된 라우트/쿼리 매개변수 이름. 컴파일러는 이를 그대로 전달하며 클라이언트(예: Flutter 엔진)는 쿼리 값을 스크린의 루트 데이터로 전달하는 데 사용한다.
- `etags` — 템플릿 버전 → **압축** 직렬화의 sha256[:16] 콘텐츠 해시. `--pretty`는 파일 바이트를 변경하지만 etag는 절대 변경하지 않는다. etag는 인코딩이 아니라 콘텐츠를 식별한다. HTTP에서는 바이트가 달라지면 강한 `ETag` 헤더도 달라져야 한다. 따라서 매니페스트 etag를 강한 검증자로 사용한다면 **압축 출력을 제공해야 한다**. 보기 좋은 JSON을 제공해야 한다면 매니페스트 해시를 약한 검증자(`W/"<hash>"`)로 전송하거나 실제 제공 바이트에서 검증자를 계산한다.

## 버전 선택

스크린과 클라이언트 앱 버전이 주어졌을 때 제공할 템플릿은 한 가지 규칙으로 결정한다. 모든 포트의 `resolve(id, appVersion)`가 이 규칙을 구현하며, 정적으로 제공하는 경우 매니페스트만으로 쉽게 다시 구현할 수 있다.

1. 스크린의 임계 버전 키를 모아 semver 순으로 정렬한다.
2. **클라이언트 버전 이하인 가장 최신 임계 버전**을 선택한다.
3. 클라이언트 버전이 없거나 빈 문자열이거나 모든 임계 버전보다 낮으면 **가장 오래된** 임계 버전을 선택한다.
4. 잘못된 클라이언트 버전(`abc`, `1.0`, `01.0.0`)이면 `Invalid semantic version: <v>` 오류가 발생한다. 이를 400으로 매핑할지 버전 없음 동작으로 폴백할지는 경계 계층에서 결정하고, 컴파일러를 호출하기 전에 처리한다.

알 수 없는 스크린 id이면 레지스트리는 아무것도 반환하지 않는다(TS는 `undefined`, Python은 `None`, Go는 `nil` 오류와 `nil` 결과). 이를 404로 매핑한다.

## 전송 방식에 독립적인 제공 알고리즘

컴파일러는 프로토콜을 강제하지 않는다. "스크린 id, 선택적 앱 버전, 선택적 캐시 검증자"를 전달할 수 있는 전송 방식이면 무엇이든 사용할 수 있다. HTTP에서는 자연스럽게 다음과 같이 매핑한다.

```text
GET /screens/<id>
    x-app-version:  2.3.0            # optional
    If-None-Match:  "be22f863ad4e95e0"   # optional

1. version  = resolve threshold from manifest (rule above)
2. etag     = manifest[id].etags[version.template]
3. if If-None-Match matches etag  ->  304 (no body)
4. else                           ->  200, body = screens/<id>/<template>.json
                                      ETag: "<etag>"
```

헤더 이름은 관례이지 계약이 아니다. `x-app-version`은 [스타터 키트](https://github.com/David-Lee-dev/sdui-flutter-starter-kit)의 클라이언트와 예제 서버가 사용하는 이름이다. 해당 저장소는 소비 측(Flutter `ScreenLoader`, 클라이언트 측 캐싱, 라우팅)의 레퍼런스이다. 같은 세 입력을 전달하는 GraphQL 필드나 gRPC 메서드도 똑같이 적합하다.

## 캐시 무효화

etag는 **버전 문자열이 아닌 콘텐츠 해시**이다. 이것이 핵심 설계 결정이다. 스크린은 하나의 템플릿 버전 디렉터리 안에서 흔히 제자리 수정된다. 버전 문자열로 캐시를 검증하면 오래된 트리를 보유한 클라이언트에 "변경 없음"이라고 응답하게 된다. 콘텐츠 etag를 사용하면 다음과 같이 동작한다.

- `template/1.0.0/**` 수정 → 재컴파일 → etag 변경 → `If-None-Match`로 재검증하는 클라이언트는 새 콘텐츠와 함께 `200`을 받는다.
- 변경 없음 → 같은 바이트, 같은 etag → `304`, 페이로드 없음.

파이프라인에 미치는 영향은 다음과 같다.

- 항상 **현재** 매니페스트의 etag를 제공한다. 매니페스트가 설명하는 스크린 파일보다 매니페스트를 더 오래 캐시해서는 안 된다.
- 출력 디렉터리를 **원자적으로** 배포한다(심볼릭 링크 전환, 버전별 접두사, 컨테이너 이미지). 한 컴파일의 `manifest.json`과 다른 컴파일의 스크린 파일을 섞으면 어느 방향으로도 etag/콘텐츠 쌍이 깨진다.
- CDN은 응답 etag가 아니라 URL을 키로 사용하고, 스크린 URL은 콘텐츠가 바뀌어도 안정적이다. 따라서 콘텐츠 주소형 또는 버전별 URL 접두사 아래에 배포한 뒤 영구 캐시하거나, TTL을 짧게 유지하고 `must-revalidate`를 사용해 수정 사항이 실제로 클라이언트에 도달하게 한다. 어느 경우든 매니페스트(또는 버전 선택을 응답하는 엔드포인트)의 TTL은 짧게 둔다.

## 배포 체크리스트

- **CI에서 컴파일한다.** 컴파일은 검증 단계이다. 순환 참조, 알 수 없는 토큰, 선언되지 않은 슬롯, 잘못된 버전은 모두 빌드를 실패시킨다. 부분 성공은 없다. 파이프라인이 아니라 템플릿을 수정한다.
- **템플릿을 신뢰할 수 있는 입력으로 취급한다.** 컴파일러는 파일을 읽고 참조를 해석하지만 작성자를 샌드박스하지 않는다. 템플릿 작성은 코드 작성과 같으므로 동일한 리뷰와 출처 관리를 적용한다.
- **인증, 롤아웃, 타기팅은 통합 계층의 책임이다.** 컴파일러는 앱 버전이 *어떤 템플릿 버전*을 받을지만 결정한다. 비율별 롤아웃, 사용자 타기팅, 인증은 모두 제공 계층에 둔다.
- **데이터는 별도의 평면이다.** 컴파일된 스크린은 정적이다. 동적 콘텐츠는 클라이언트 엔진이 사용하는 데이터 메커니즘을 통해 전달된다(스타터 키트는 스크린과 `POST /v3/data` 작업 엔드포인트를 함께 사용한다). 데이터를 변경하려고 템플릿을 다시 컴파일하지 않는다.
- **파이프라인마다 포트 하나를 고정한다.** 포트들이 바이트 단위로 동일하므로 혼용해도 *안전*하지만, 단일 포트 파이프라인을 사용하면 도구 체인의 드리프트가 빌드 캐시와 인시던트 타임라인에 유입되지 않는다.
